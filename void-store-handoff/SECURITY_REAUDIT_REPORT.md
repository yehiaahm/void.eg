# تقرير الفحص الأمني الثاني — VOID Store

التاريخ: 2026-11-14 · النطاق: الكود الحالي بعد إصلاحات VOID-01..06 و PV-1..5، + تغييرات المنتجات الجديدة (migrations V11–V21 وملفات الواجهة الجديدة).
**ما اتغيّرش أي ملف كود في الفحص ده** — ده فحص وتقرير بس.

> **ملاحظة صريحة:** مفيش موقع "آمن تماماً". اللي ممكن نوصله هو إن الطرق المعروفة للاختراق تتقفل، وإن أي محاولة تتكشف بسرعة. التقرير ده بيقولك إيه اتقفل، وإيه لسه مفتوح، وإزاي الهاكر ممكن يدخل من اللي فاضل.

---

## 0. حالة الجهاز (عاجل)

- **ديسك C: فاضي 0 جيجا.** ده ممكن يوقّف أو يبوّظ قاعدة البيانات الـ dev (`void-mysql`) وأي حاجة بتكتب على Docker. أنا وقفت اختباري وحذفت بس الـ container بتاعي (`void-audit-mysql`) وملفاتي المؤقتة؛ **ما مسحتش أي حاجة تخصك.** حرّر مساحة (مثلاً `docker system df` لتشوف الصور القديمة غير المستخدمة) قبل ما تكمل شغل.
- بسبب كده **الاختبار الحي (DAST) اتقطع**: الأقسام A–E خلصت، والأقسام F–N (منطق الشراء، IDOR حي، حقن، رفع ملفات، rate-limit حي، جلسات) **ماتجرّبتش حي**. هما متغطيين بالـ integration tests (اتشغلت النهارده) وبمراجعة الكود، لكن مش بـ HTTP حي.

## 1. اللي اتأكد منه فعلاً النهارده

| الفحص | النتيجة | الدليل |

| Unit tests | 102/102 (آخر تشغيل قبل الفحص، الكود ماتغيّرش بعده) | |

**تحذير على دقة الاختبار:** أول جولة DAST اشتغلت وقراءة `backend/local.properties` غيّرت السر والـ owner (لأن ملف `local.properties` بيغلب متغيرات البيئة). عشان كده اختبارين (توكن منتهي + issuer غلط بالسر "الحقيقي") **مش معتمدين**؛ هما متغطيين في `SecurityConfigJwtTest`. وده نفسه تنبيه تشغيل: **أي `local.properties` في مكان تشغيل السيرفر هيغلب متغيرات البيئة** — ما تسيبوش على السيرفر.

## 2. إزاي الهاكر ممكن يدخل — مرتبة بالأخطر

### 🔴 1) حساب الـ Owner/Admin (باب أمامي واحد بدون MFA)
كلمة سر واحدة بتفتح كل حاجة: بيانات كل العملاء (اسم/تليفون/عنوان/إيميل)، الطلبات، الكوبونات، تصدير 10,000 طلب CSV.
- مفيش **MFA/TOTP**. لو الباسورد اتخمّن/اتسرّب/اتعمل له phishing = اختراق كامل.
- أقل طول لباسورد الـ staff 10 حروف بس، وللعملاء 8، ومفيش فحص كلمات شائعة/مسرّبة.
- **المطلوب:** MFA للـ ADMIN/OWNER، وتقييد `/admin` و`/api/v1/admin/**` بـ IP allowlist أو Cloudflare Access/VPN عند Caddy، وباسورد owner طويل (16+) من password manager.

### 🔴 2) جهازك الحالي: MySQL و Mailpit مفتوحين على الشبكة
الفحص أكد (`docker ps`): `void-mysql` على `0.0.0.0:3307` و`void-mailpit` على `0.0.0.0:8025/1025`، وبباسوردات dev المعروفة في `docker-compose.yml` (مكتوبة في الريبو). أي حد على نفس الـ Wi-Fi/الشبكة يقدر يدخل الداتابيز كـ root ويقرأ كل الإيميلات (روابط reset password).
- **المطلوب:** `"127.0.0.1:3307:3306"` و`"127.0.0.1:8025:8025"` و`"127.0.0.1:1025:1025"` في الـ compose، وإعادة تشغيل الـ containers، وما تستخدمش داتا حقيقية للعملاء على الجهاز ده.

### 🔴 3) النشر نفسه (السيرفر)
ده برّه الكود وأنا ماقدرش أفحصه من هنا، وأغلب الاختراقات الحقيقية بتيجي منه:
- صورة Docker القديمة **`void-store:test`** (اتبنت 2 أكتوبر، قبل الإصلاحات) على جهازك: **فيها السر الافتراضي القديم.** ما تنشرهاش؛ ابنِ من جديد.
- لازم: SSH بمفاتيح فقط وبدون root، جدار ناري (80/443 بس)، `fail2ban`، تحديثات تلقائية للنظام، **ما تنشرش بورت 8080 ولا 3306**، `.env` صلاحياته 600 وبره أي ريبو، Docker socket مش متاح للـ container.
- لو هتحط Cloudflare قدام الموقع: لازم تضبط `trusted_proxies` في Caddy (وإلا Caddy هيشوف IP كلاودفلير بدل العميل — شوف نقطة 8).

### 🟠 4) سرقة حسابات العملاء (credential stuffing)
- حد أدنى 8 حروف بدون فحص كلمات مسرّبة (VOID-14). الإصلاح اللي عملته بيحدّ المحاولات (40/IP و10 فاشلة/حساب لكل 15 د) لكنه مش بيمنع باسورد ضعيف.
- **المطلوب:** حد أدنى 10–12 + رفض الكلمات الشائعة، وCloudflare Turnstile على login/register/checkout/contact.

### 🟠 5) الجلسات بعد التعطيل أو تغيير الباسورد (VOID-07 — لسه مفتوح)
- موظف/عميل اتعطّل: التوكن الحالي يفضل شغّال لحد 15 دقيقة. (الكود بيقرأ الدور من التوكن مش من الداتابيز.)
- تغيير الباسورد **مابيلغيش** الـ refresh tokens القديمة (reset بيلغيها، change لأ — أنا رجّعتها بقصد في المرحلة السابقة عشان ما أغيّرش سلوك، ولازم تتقفل). لو حد سرق refresh token، تغيير الباسورد مش هيطرده لمدة 30 يوم.
- **المطلوب:** إلغاء كل الـ refresh tokens عند تغيير الباسورد، وتقليل عمر توكن الـ admin أو فحص `tokenVersion`.

### 🟠 6) غياب CSP (VOID-08 — اتأكد حي: مفيش CSP)
مفيش sink XSS معروف في الكود (React بيعمل escape، والـ `dangerouslySetInnerHTML` الوحيد على SVG ثابت)، لكن لو ظهرت ثغرة XSS مستقبلاً، من غير CSP تقدر تسرق جلسة الأدمن. أضف CSP في Caddy (ولاحظ إن `index.html` فيه `onload=` inline لازم يتشال).

### 🟠 7) بريد الدومين (برّه الكود)
من غير **SPF + DKIM + DMARC** على دومين الإيميلات، أي حد يقدر يبعت إيميل "طلبك اتأكد" مزيّف باسم VOID بروابط تصيّد. وإيميلات الطلبات دلوقتي فيها رابط تتبع بـ token، فلازم تتأكد إنها بتوصل Inbox مش Spam.

### 🟡 8) الاعتماد على الـ proxy في معرفة IP العميل
`ClientIpResolver` بيصدّق `X-Forwarded-For` من الـ proxy الموثوق بس (تمام). المخاطر التشغيلية:
- لو كل الزباين ظهروا بـ IP واحد (Docker NAT على بعض الأجهزة، Cloudflare بدون إعداد، **أو CGNAT بتاع شبكات المحمول في مصر**) فحدود `10 طلبات/10 د` و`40 login/15 د` لكل IP ممكن **تمنع عملاء حقيقيين وقت الدروب**. اتأكد من لوج Caddy إنه بيسجّل IP العميل الحقيقي، وراقب 429 وقت أول دروب، وارفع الحدود لو لزم.
- في الاتجاه العكسي: لو بورت التطبيق اتنشر مباشرة، الحدود بتفضل شغالة (الـ header بيتتجاهل) — ده اتختبر unit، مش حي.

### 🟡 9) قفل الحساب ممكن يتحول لهجوم DoS
10 محاولات فاشلة على إيميل = الحساب مقفول 15 دقيقة لكل العناوين، **بما فيهم الـ Owner الحقيقي**. مهاجم يقدر يبقّي الأدمن برّه لَوج-إن باستمرار (الجلسات الجارية مش بتتأثر). الحل: MFA + IP allowlist للأدمن، أو قفل أخف على (حساب+IP) مع حد عالٍ على الحساب كله، أو إشعار للـ owner.

### 🟡 10) باقي نقاط VOID الأصلية اللي ماتصلّحتش
- **VOID-10:** مطابق المسار يعتمد على `getRequestURI` الخام — اتجرّب حي ومفيش تخطي (كل الـ controllers بتفحص بنفسها)، لكنه لسه "قنبلة موقوتة" لأي controller جديد.
- **VOID-11:** تسجيل بإيميل موجود بيرجع 409 (اتأكد حي) = تعداد حسابات.
- **VOID-12:** أي حد يعرف رقم تليفون يقدر يكتب فوق بيانات الـ waitlist بتاعته.
- **VOID-13:** `COOKIE_SECURE` الافتراضي `false` (الـ compose بيضبطه true، أي منصة تانية لا). HSTS على Caddy بس.
- **VOID-15:** `npm audit`: vite (high — dev server بس) و react-router (moderate — مش قابل للاستغلال هنا). `npm audit fix` بيحل vite.
- **VOID-16:** صور Docker بدون pin، بدون `cap_drop`/حدود موارد.
- **VOID-17/18:** الـ Owner لما يضيف staff بإيميل عميل موجود بيستبدل باسورده؛ أي STAFF يقدر يصدّر 10,000 طلب ويسجّل refund بأي مبلغ بدون موافقة تانية.
- **VOID-21:** الريبو **مش git** → مفيش history أفحصه للأسرار، ومفيش CI.

### 🟡 11) نقاط جديدة من الفحص ده
- **Health endpoint بيرجع 503** لما SMTP مش شغّال (اتأكد حي: `MailHealthIndicator`). والـ `HEALTHCHECK` في Dockerfile بيعتمد عليه → الـ container هيبان "unhealthy" طول ما مفيش `MAIL_HOST` (والـ docs بتقول الإيميل اختياري). مش ثغرة، لكن بيخلّي المراقبة مش موثوقة. الحل: `management.health.mail.enabled=false`.
- **توكن التتبع** مشتق من نفس سر JWT (لو السر اتسرّب التوكنات تتزوّر) وبيتحط في الـ URL (history/لوجات Caddy). الأفضل سر منفصل + مسح `t` من الـ URL بعد التحميل.
- **الـ rate limiter in-memory:** بيقفل لما يوصل 100,000 key (fail-closed). هجوم موزّع كبير ممكن يملّيه ويوقّف login/checkout مؤقتاً. وبيضيع عند إعادة التشغيل ومش هيشتغل لو شغّلت أكتر من نسخة.
- **مفيش حد لحجم الـ JSON body في التطبيق** (Caddy بيسمح لحد 40MB للرفع). الحقول محدودة بالـ validation بعد القراءة. أضف حد في Caddy للمسارات العادية.
- **رفع الصور:** بيتحقق من الـ magic bytes ويرفض HTML/SVG، لكن PNG بنص script في آخره بيتقبل (بيتقدّم كـ `image/png` + `nosniff` فمش خطر). ده من مراجعة الكود، **مش اتجرّب حي** النهارده.
- **migrations V11–V21 الجديدة:** بيانات منتجات بس (INSERT/UPDATE/DELETE)، مفيش مشكلة أمنية فيها. المنتجات الجديدة بتنادي صور من `/assets/products/` (ملفات ثابتة) تمام.

## 3. اللي ناقص عشان تقول "جاهز للإطلاق" (قائمة مرتبة)

**قبل الإطلاق (لازم):**
1. MFA للأدمن + `/admin` وراء IP allowlist/Cloudflare Access، وباسورد owner قوي.
2. قفل بورتات MySQL/Mailpit على `127.0.0.1` (وإيقاف أي بورت dev مفتوح على الشبكة).
3. بناء صورة Docker **جديدة** من الكود الحالي، وحذف `void-store:test` القديمة. تأكد إن `JWT_SECRET` و`COOKIE_SECURE=true` و`DB_*` متضبطين، وإن مفيش `local.properties` على السيرفر.
4. تقوية السيرفر (SSH مفاتيح، firewall، fail2ban، تحديثات، بورتات 80/443 بس).
5. CSP + حد لحجم الـ body في Caddy، وتأكيد HSTS شغّال.
6. إلغاء الجلسات عند تغيير الباسورد، وباسورد ≥ 10–12 + فحص الشائع.
7. SPF/DKIM/DMARC + اختبار وصول إيميلات الطلب.
8. تأكيد إن Caddy بيشوف IP العميل الحقيقي (وتظبيط `trusted_proxies` لو Cloudflare)، وإيقاف mail health أو ضبط SMTP.
9. **Backups يومية خارج السيرفر + تجربة restore فعلية** (DEPLOY.md فيه الأوامر).
10. تشغيل `StoreFlowTests` + إعادة الـ DAST الكامل (الأقسام F–N) على staging بعد تحرير مساحة الديسك.

**بعد الإطلاق / مستمر:**
- جمع لوج `AUDIT` (stdout) في مكان خارجي وتنبيهات على: `auth.login.failed` بكثرة، `auth.refresh.reuse`، `staff.*`، `export.*.large`، `rate_limit.exceeded`، `authz.denied`.
- Turnstile على login/checkout/contact، وOTP للتليفون لو حصل hoarding للمخزون (PV-4 لسه "بيقلل" مش "بيمنع").
- فحص تبعيات مستمر: Dependabot/Renovate + OWASP Dependency-Check أو Trivy للصور (لسه ماتشغّلوش — ماسحتش تبعيات الـ Maven بأداة SCA). إصدارات الـ backend الحالية: Spring Boot 4.1.1، Tomcat 11.0.24، Spring Security 7.1.1، Hibernate 7.4.5، nimbus-jose-jwt 10.9.1، MySQL connector 9.7.0 — **ماقدرتش أتأكد من حالة CVE لها بعد معرفتي**، فلازم أداة SCA.
- حط المشروع في Git (private) + secret scanning (gitleaks) + CI بيشغّل الـ tests.
- مستخدم MySQL منفصل للتطبيق بصلاحيات DML فقط، وآخر للـ migrations (حالياً `void` بيعمل الاتنين).
- سياسة حفظ/حذف بيانات العملاء (قانون حماية البيانات الشخصية المصري 151/2020) وصفحة الخصوصية متطابقة مع اللي بيتجمع فعلاً.
- لما تضيف Paymob: تحقق HMAC من الـ webhook، idempotent، مقارنة المبلغ، وبدء بـ test mode.
- اختبار اختراق خارجي (pentest) من طرف مستقل قبل الإطلاق الكبير.

## 4. الخلاصة
- **الكود نفسه** (حقن، XSS، IDOR، تعديل أسعار، تزوير JWT، تخطي المصادقة) **طلع نضيف في كل اللي اتجرّب**، والـ 20 integration test على MySQL حقيقي نجحوا.
- **اللي هيخلّي الهاكر يدخل غالباً مش ثغرة كود**: حساب أدمن بدون MFA، جهاز/سيرفر مفتوح البورتات، صورة قديمة فيها السر الافتراضي، إيميل دومين من غير SPF/DKIM، باسوردات ضعيفة للعملاء، وعدم وجود مراقبة للوجات.
- **الحكم:** "يحتاج تحسينات قبل الإنتاج" — النقاط 1–10 فوق هي الحد الأدنى. وده مش ضمان إنه آمن تماماً؛ لازم DAST كامل على staging واختبار اختراق مستقل.
